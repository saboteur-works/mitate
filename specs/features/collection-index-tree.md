# Feature Spec: Index a folder collection and browse its tree

**Source:** Feature 1 in `specs/product/media-organizer-mvp.features.md`
**Product spec:** `specs/product/media-organizer-mvp.md` (product FR-1, FR-7, FR-8, FR-9, FR-10, FR-17; product US-1, US-3)
**Branch:** `feat/collection-index-tree`
**Length note:** This spec is longer than the 500-word guideline. The feature is the first one in the repository, so it also covers the app scaffold, the supported-type registry and the read-only check that every later feature reuses. IDs below are local to this document. Each requirement names the product requirement it implements.

## Overview
A user creates a named collection from one or more folders, and the app finds every supported media file in them at any depth and shows the result as a folder tree that mirrors the disk. The collection and its folder access are still there after the app restarts. The feature also lands the first application code in the repository (a minimal Electron app on macOS), the supported-type registry that later features read, and a reusable check that proves the app has not changed anything in a collection's folders. Without it nothing else in the MVP has an index to work on.

## Goals
- A user can create a named collection from folders chosen in a folder picker and browse every supported media file in it as a folder tree.
- A collection and its folders are present after a restart without the user re-selecting folders, under the chosen distribution channel.
- The supported-type registry is the single source of extension-to-media-kind mapping, and later features read it instead of keeping their own lists.
- Any feature's tests can run one shared before/after check that fails if a file, timestamp or extended attribute inside a collection's folders changed.
- All app data (collections, folder records, index, folder access) lives in app storage, in a design that does not prevent adding encryption later.

## Non-goals
- Adding a folder to an existing collection (Feature 3; OQ-7), renaming or deleting collections, removing folders, switching collections, overlap detection and de-duplication (Feature 3). Until Feature 3 ships, overlapping folders may show a file twice.
- Reveal in Finder and path display (Feature 2), flat type views (Feature 4), and preview or playback of any file (Features 6 to 8).
- Scan progress display and browsing while a scan is running (Feature 5). This feature only fixes the boundary described in FR-12.
- Numeric performance targets (product FR-20 is blocked on a measurement task).
- Encryption of app storage, and live index updates when files change on disk (v1).

## User stories
- US-1: As a creative professional, I want to group folders from different drives into a named collection and browse its files as a folder tree so that each project or archive has its own workspace. (Product US-1.)
- US-2: As a creative professional, I want to be sure the app never changes my files so that I can point it at irreplaceable archives. (Product US-3.)

## Functional requirements
1. FR-1: Users MUST be able to create a collection with a non-empty name by choosing one or more folders in a folder picker. The picker MUST allow selecting directories only, and the app MUST offer no way to add an individual file. This feature covers only folders chosen when the collection is created; adding a folder to an existing collection belongs to Feature 3 (OQ-7). A picked folder that cannot be opened for listing at creation (for example EACCES or EPERM) MUST be rejected with an error naming the folder, and nothing is created (OQ-10). [US-1] (Product FR-1.)
2. FR-2: Collection records, folder records (including each folder's absolute path) and the file index MUST be stored in app storage and MUST be present after the app is quit and relaunched. [US-1] (Product FR-7, FR-8.)
3. FR-3: After a relaunch, the app MUST be able to read every previously added folder that is still available, without showing a folder picker or any other prompt asking the user to re-select it. The MVP ships outside the Mac App Store (Developer ID signing and notarization, OQ-1), so folder access is not sandboxed and no security-scoped bookmarks are used; the persisted folder-access data is read and written only through the storage module (FR-18) so bookmarks can be added later. A macOS privacy prompt for a removable or network volume is an operating-system prompt, not a request to re-select the folder, and is not excluded by this requirement. [US-1] (Product FR-7.)
4. FR-4: If a previously added folder cannot be accessed at launch, the app MUST keep the collection and folder records and MUST mark that folder as unavailable. It MUST NOT delete the folder or silently drop its files from the index. The tree MUST keep showing that folder's stored files, each marked "unavailable"; they MUST NOT be hidden (hiding is v1 FR-7). [US-1] (Product FR-7.)
5. FR-5: The app MUST discover files in each folder and all its subfolders at any depth, and MUST index each file whose extension is in the supported-type registry. Extension matching MUST be case-insensitive. [US-1] (Product FR-8.)
6. FR-6: Discovery MUST treat as hidden, and skip, every file and folder whose name starts with ".", and MUST NOT descend into skipped folders. The macOS hidden flag is not consulted; it is revisited with v1 FR-9 (OQ-5). [US-1] (Product FR-9.)
7. FR-7: Discovery MUST NOT index the contents of package bundles. A package is a directory whose name ends in an extension from one fixed, named list kept in one place: .app, .photoslibrary, .bundle, .framework, .rtfd, and similar macOS package extensions added to that list. The macOS package attribute is not consulted; it is revisited with v1 FR-9 (OQ-5). [US-1] (Product FR-9.)
8. FR-8: Discovery MUST NOT follow symlinks to folders and MUST skip symlinks to files, so a symlink to a file is not indexed. A file or folder reachable only through a symlink MUST NOT appear in the index. [US-1] (Product FR-9.)
9. FR-9: The supported-type registry MUST be one module with one data table. Each entry maps one lowercase extension to exactly one media kind (image, audio, video or document) and MAY carry a subtype (for example RAW). It MUST expose a lookup from extension to entry and a listing of entries by kind. No extension MAY appear in two entries. [US-1] (Supports product FR-8, FR-14.)
10. FR-10: The registry MUST contain every extension named in product FR-12, FR-14, FR-21 and FR-22, except those pending product FR-23, and MUST contain no other extension except the aliases jpg (jpeg), tif (tiff) and aif (aiff). The initial table is: image = jpeg, jpg, png, gif, heic, heif, tiff, tif, bmp, webp, avif, psd, exr, tga; image with subtype RAW = cr2, cr3, nef, arw, dng, raf, orf, rw2, pef, srw, iiq, 3fr; audio = mp3, aac, m4a, wav, flac, ogg, opus, aiff, aif, wma; video = mp4, mov, m4v, 3gp, mkv, webm, mpg, dv, wmv, avi, flv; document = pdf, txt, epub, cbz. Codec-defined formats that cannot be identified by extension (ProRes, DNxHD, ALAC, AC-3) are not registry entries. The registry says what is indexed, not what can be previewed or played; later features keep their own capability tables keyed on the registry. The formats pending product FR-23 (jxl, caf, ac3, ts, mts, m2ts) are NOT registered until FR-23 unblocks. Consequence: files with these extensions, including camcorder .ts, .mts and .m2ts files, are not indexed in the MVP. epub and cbz are kind document and are not previewed. RAW entries are kind image with subtype RAW and appear in the Images view (OQ-3). [US-1] (Product FR-8, FR-14.)
11. FR-11: Users MUST be able to browse a collection as a folder tree whose folders and files mirror the on-disk structure beneath each added folder, showing for each file its name. A collection's top-level (root) folders, the folders the user added, MUST always be shown, marked "unavailable" when they cannot be read, even if they contain no supported files or no stored files. Every folder below the roots MUST be shown only if it contains at least one supported file at any depth. Within each folder, subfolders MUST be listed before files, and both MUST be sorted by name using a case-insensitive natural numeric order, so that IMG_2 sorts before IMG_10. The tree view MUST render only the nodes that are visible or expanded, so the number of rendered nodes does not grow with the size of the index. [US-1] (Product FR-10; scale constraint.)
12. FR-12: Discovery MUST run outside the UI's rendering path so the window stays interactive during a scan. This feature MAY make results visible only when a scan completes; publishing results incrementally and showing progress belong to Feature 5, which MAY change how discovery commits results. [US-1] (Boundary with product FR-18, FR-19.)
13. FR-13: The app MUST NOT create, modify, move, rename or delete any file, folder or extended attribute inside a collection's folders. App storage MUST be located outside any collection folder. [US-2] (Product FR-17.)
14. FR-14: The repository MUST contain a reusable read-only check usable from any feature's tests. Given a directory tree, it MUST record a snapshot of every entry: relative path, entry type, size, mode, a content hash for files, modification time, change time, birth time, access time, and each extended attribute's name and value hash. It MUST compare two snapshots and report each entry that was added, removed or differs, naming the differing field. It MUST exit with failure or throw when any difference is found, except for access time (FR-15). [US-2] (Product FR-17.)
15. FR-15: The check MUST report access-time differences separately from all other differences, and a configuration flag MUST decide whether they fail the check. The default is never to fail on access time while always reporting it (OQ-2). The check MUST be ordered so its own reads do not appear as app changes: access time for the "before" snapshot MUST be recorded after the "before" content hashing, and access time for the "after" snapshot MUST be recorded before the "after" content hashing. [US-2] (Product FR-17.)
16. FR-16: The check MUST have its own tests showing it detects each of these changes made to a fixture tree: a byte changed in a file, a file created, a file deleted, a file renamed, a modification time changed, an extended attribute added, an extended attribute value changed, and an extended attribute removed. It MUST also have a test showing that two snapshots with nothing in between report no differences, including access time. [US-2] (Product FR-17.)
17. FR-17: This feature's tests MUST run the check around the full flow (create a collection, scan, browse the tree, quit, relaunch) on a fixture tree, and the check MUST report no differences. The fixture tree MUST contain nested folders at least four levels deep, supported and unsupported files, a hidden file and folder, a package bundle, a symlink to a folder and a symlink to a file, and files with extended attributes. [US-2] (Product FR-17.)
18. FR-18: All reads and writes of collection records, folder records, the index and folder-access data MUST go through one storage module, and the storage location MUST be configurable in one place. The design MUST NOT require plaintext access to the stored files by any other module, so that encrypting app storage later does not require changes outside the storage module. [US-1] (OQ-5 resolution; privacy constraint.)
19. FR-19: The repository MUST contain a runnable Electron application for macOS with commands to launch it, to build it and to run its automated tests. The MVP uses plain JavaScript, npm, and a JSON or key-value file store behind the storage module (FR-18) (OQ-4); the test framework is Vitest for unit and integration tests and Playwright's Electron support for end-to-end tests (OQ-9); compatibility of Playwright's Electron support with Electron 44 is unverified and the first scaffold task verifies it. TypeScript and SQLite are the recorded future option. Known risk: a JSON store is not expected to scale to hundreds of thousands of files (unmeasured); the FR-18 module boundary keeps a later swap contained. [US-1] (Scaffold; runtime constraint.)
20. FR-20: Each collection MUST have a user-triggered rescan action that re-runs discovery over its available folders and updates the index. On launch the app MUST show the stored index without rescanning. [US-1] (Product FR-26; boundary with product FR-7, FR-8.)
21. FR-21: A measurement MUST be run and recorded: read a fixture file with a plain `cat`, compare its access time before and after, on each volume type (internal APFS, external drive, network volume). Until it exists, FR-15's default stays never-fail. Moving to "fail where reads leave access time unchanged" depends on its result (OQ-2). [US-2] (Product FR-17.)

## Open questions
- OQ-1 [Resolved 2026-10-18]: Which distribution channel does the MVP ship through: the Mac App Store (sandboxed, persisting folder access with security-scoped bookmarks and the user-selected-folder entitlement), outside the store with Developer ID signing and notarization (sandbox optional, and folder access then depends on macOS privacy permissions for each location, including removable and network volumes), or both? The channels differ in how FR-3 is met and whether it is met for network volumes. — Impact: FR-3, FR-4, FR-19, and the storage design in FR-2.
  Answer: Developer ID signing and notarization only, outside the Mac App Store, for the MVP. Folder access persistence goes through the storage module (FR-18) so security-scoped bookmarks can be added later (FR-3). Removable and network volumes may raise macOS privacy prompts. The App Store sandbox experiment (avconvert, Quick Look, network volumes) has not been run.
- OQ-2 [Resolved 2026-10-18]: Does a change to a file's access time count as a violation of read-only? Reading a file can update its access time on some volumes, and whether this app's reads do so on APFS, external drives and network volumes is not measured. Options: always fail, never fail but always report, or fail only on volumes where a measurement shows reads without the app's participation leave it unchanged. The measurement that would settle it is reading a fixture with a plain `cat` and comparing access time on each volume type. — Impact: FR-14, FR-15, FR-16, FR-17.
  Answer: Never fail on access-time change; always report it separately. FR-15's configuration flag stays. A measurement is to be run (FR-21); moving to "fail where reads leave access time unchanged" depends on its result.
- OQ-3 [Resolved 2026-10-18]: What exactly does the registry contain for items the product spec does not fully fix? Specifically: (a) are the formats pending product FR-23 (jxl, caf, ac3, ts, mts, m2ts) registered now or only when that requirement unblocks; (b) are epub and cbz documents; (c) do RAW files show in the Images view (Feature 4) or only under a RAW subtype. — Impact: FR-9, FR-10.
  Answer: (a) jxl, caf, ac3, ts, mts, m2ts are not registered until product FR-23 unblocks; camcorder .ts, .mts and .m2ts files are therefore not indexed in the MVP (FR-10). (b) epub and cbz are kind document, with no preview. (c) RAW is kind image, subtype RAW, and appears in Images.
- OQ-4 [Resolved 2026-10-18]: Which application toolchain does the scaffold use: language (TypeScript or JavaScript), bundler and Electron packaging tool, package manager, storage engine (for example an embedded SQL database or a key-value store, including how it supports later encryption), and test framework including how Electron end-to-end tests run? None is settled in the product spec or concept. — Impact: FR-2, FR-12, FR-16, FR-17, FR-18, FR-19.
  Answer: Plain JavaScript, npm, and a JSON or key-value file store for the MVP, behind the FR-18 storage module (FR-19). TypeScript and SQLite are the recorded future option. Known risk from triage: a JSON store is not expected to scale to hundreds of thousands of files (unmeasured); the FR-18 boundary contains the later swap. The test framework is Vitest with Playwright for Electron end-to-end tests: see OQ-9.
- OQ-5 [Resolved 2026-10-18]: How are "hidden", "package" and symlinked files defined precisely? Options for hidden: leading "." only, or also the macOS hidden flag. Options for packages: a fixed list of extensions, or the macOS package attribute. A symlink to a file can be skipped entirely or indexed as a file; product FR-9 says only that symlinks are not followed. — Impact: FR-6, FR-7, FR-8, FR-17.
  Answer: Hidden means a name beginning with "." (FR-6). Packages are a fixed, named extension list: .app, .photoslibrary, .bundle, .framework, .rtfd and similar (FR-7). The macOS hidden flag and package attribute are revisited with v1 FR-9. Symlinks to files are skipped, same as symlinked folders (FR-8, product FR-9).
- OQ-6 [Resolved 2026-10-18]: When is the index refreshed? After a relaunch, the stored index can be shown as it was, or the folders can be rescanned, or the user can trigger a rescan. Live updates are v1. The choice also decides what the tree shows for a folder marked unavailable (FR-4). — Impact: FR-2, FR-4, FR-5, FR-12.
  Answer: On launch the stored index is shown. A user-triggered rescan action per collection is added (FR-20). An unavailable folder shows its stored files marked "unavailable", not hidden (FR-4; hiding is v1 FR-7). Rescan is mandated by product FR-26.
- OQ-7 [Resolved 2026-10-18]: Does adding a folder to an existing collection belong to this feature or to Feature 3 (which owns the confirmation in product FR-5)? This feature covers adding folders when a collection is created. — Impact: FR-1, and the scope of Feature 3.
  Answer: Adding a folder to an existing collection is Feature 3. This feature covers folders chosen at collection creation only (FR-1). Product FR-27 (add a folder to an existing collection) states it and is assigned to Feature 3.
- OQ-8 [Resolved 2026-10-18]: What does the tree show beyond file names: are folders with no supported files shown, and what is the sort order of folders and files? — Impact: FR-11.
  Answer: Show only folders containing at least one supported file at any depth; folders first, then files; case-insensitive natural numeric sort (IMG_2 before IMG_10) (FR-11).
  Refinement 2026-10-18 (user decision during implementation): the show-only-folders-with-supported-files rule applies to every folder below the collection's root folders. Root folders are always shown, marked "unavailable" when unreadable, even when empty. Why: a folder whose scan fails at creation (after passing the FR-1 readability check) has no stored files and would otherwise vanish from the tree, conflicting with FR-4 (kept and marked unavailable).
- OQ-9 [Resolved 2026-10-18]: Which test framework does the scaffold use, including how Electron end-to-end tests run? The user did not choose one when resolving OQ-4. — Impact: FR-16, FR-17, FR-19.
  Answer: Vitest for unit and integration tests; Playwright's Electron support for end-to-end tests (including the quit-and-relaunch flow in FR-17). Compatibility of Playwright's Electron support with Electron 44 is unverified; the first scaffold task verifies it.
- OQ-10 [Resolved 2026-10-19]: When the user picks a folder that cannot be opened for listing (EPERM) at collection creation, should creating the collection fail or add the folder as unavailable? — Impact: FR-1, FR-4.
  Answer: Creating the collection fails with an error naming the folder and EPERM (current behaviour); the folder is NOT added as unavailable and nothing is created. A folder refused after creation is still marked unavailable (FR-4, unchanged).

## Out of scope (deferred)
- Collection rename, delete, switching and folder removal (Feature 3).
- Overlap warnings and showing each file once (Feature 3).
- Incremental scan publishing and scan progress (Feature 5).
- Path display and Reveal in Finder (Feature 2).
- Flat type views (Feature 4), preview and playback (Features 6 to 8).
- Numeric scan and browse performance targets (product FR-20, after the measurement task).
- Encryption of app storage (post-MVP; FR-18 only keeps it possible).
- Live index updates, opt-in hidden files, packages and symlinks (v1).
