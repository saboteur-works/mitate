# Feature Spec: Manage and switch between collections

**Source:** Feature 3 in `specs/product/media-organizer-mvp.features.md`
**Product spec:** `specs/product/media-organizer-mvp.md` (product FR-2, FR-3, FR-4, FR-5, FR-6, FR-27; FR-17 applies to every action here; product US-1, US-2, US-3, US-5 where FR-6 cites it; Constraints: read-only, macOS first)
**Branch:** `feat/collection-management`
**Depends on:** Feature 1 (`specs/features/collection-index-tree.md`, shipped) and Feature 2 (`specs/features/location-reveal.md`, shipped). IDs below are local to this document. Each requirement names the product requirement it implements.
**Length note:** This spec is longer than the 500-word guideline. It covers six product requirements that share one data-model decision (a folder in several collections, kept as separate per-collection records) and one set of resolved open questions.

## Overview
A user keeps several named collections, can rename and delete them, switch the active one, add a folder to an existing collection and remove a folder from one, and may put the same folder in more than one collection. A folder that sits inside a folder already in the collection (or is the same folder) is refused, with a message naming the folder that covers it. A folder that contains folders already in the collection asks for confirmation naming them, and on confirm replaces them. At creation, picked folders that nest are reduced to the outermost ones and the user is told. This was revised on 2026-10-21 (see the note under the resolved questions). A file reachable through more than one folder of the same collection appears once, which also holds for collections stored before the revision that still contain nested folders. Feature 1 can create collections and select one by clicking it in a list, but it cannot rename, delete, add to or remove from a collection, it stores each folder under exactly one collection, and it can show a file twice when roots overlap. Nothing in this feature changes anything on disk in a collection's folders.

## State of the shipped code (measured by reading the code, 2026-10-20)
- Storage, `src/main/storage/index.js`:
  - `FORMAT_VERSION` is 1. `load` throws `STORE_OPEN_FAILED` with reason `unsupported-format` for any other `version` value, or when `version` is missing. No migration code exists.
  - `CollectionRecord { id, name, folderIds, createdAt }`. `FolderRecord { id, collectionId, path, unavailable }`: a folder record names exactly one collection. `FileRecord` carries `folderId` and `collectionId`; `replaceFolderIndex` stamps both from the folder record. The index is stored per folder id (`state.index[folderId]`).
  - `removeCollection(id)` drops every folder whose `collectionId` equals the id, with that folder's index and access data, then the collection. `removeFolder(id)` drops the folder with its index and access data. Neither is aware of any other collection. Neither updates `CollectionRecord.folderIds` of the owning collection. `putCollection` and `putFolder` replace whole records. There is no rename function; `putCollection` with a new `name` would do it.
  - `transaction(fn)` runs a synchronous callback and persists once with write-then-rename; nested transactions throw. Mutators outside a transaction persist one write each.
- `src/main/startup.js`: an older format (found < supported) gives the message "uses an older data format (format N) that this version of the app cannot open (it reads format 1). The file has not been changed."; a newer format gives "was written by a newer version of this app ... Install a newer version of the app". The older format is rejected, not migrated. `startStorage` only reads the store file; a failed open never writes, overwrites, deletes or renames it.
- `src/main/collections/service.js`: `createCollection(name, directories)` validates (non-blank name, at least one folder, absolute readable directories, duplicates collapsed after `path.resolve`, folder must not contain the app storage file) and stores collection, folders and indexes in one transaction. There is no add-folder, remove-folder, rename or delete function. No code compares one folder path with another, so there is no overlap detection at creation or anywhere else. `listCollectionSummaries` refreshes each folder's `unavailable` flag (readability check) and persists changes; `findIndexedFile(path)` returns the first stored record whose `path` equals the argument.
- `src/main/collections/rescan.js`: `rescanCollection(id)` keeps an in-flight `Set` keyed by collection id; a second call for the same collection rejects with `RESCAN_IN_PROGRESS`. It reads `storage.listFolders(collectionId)` once at the start, scans every folder, then applies all results in one transaction; a folder removed from storage meanwhile is reported in `summary.skipped` and nothing is written for it. No other operation uses this guard.
- `src/main/ipc.js` `CHANNELS`: `folders:pick`, `collections:create`, `collections:list`, `collections:getView`, `collections:rescan`, `files:reveal`. `src/main/preload.js` mirrors them on `window.mediaOrganizer`. There are no channels for rename, delete, add folder, remove folder, or a confirmation. `guard` returns `{ ok, error, code? }`.
- Renderer, `src/renderer/create-collection.js`: a collection list (`data-testid="collection-list"`, one `collection-item` per collection showing name and "(N folders)") already exists. Clicking an item calls `selectCollection`, which loads `collections:getView`, calls `TreeView.show`, highlights the item (`collection-selected`) and dispatches `collection-selected` on `document` with `detail.collectionId`; a token discards a stale slower response. At launch `selectedCollectionId` is null and no tree is shown until the user clicks an item; nothing persists the active collection. So a click-to-switch list exists for the tree view (the only view), but there is no rename, delete, add-folder or remove-folder control, and the list shows only a folder count, not the folders.
- `src/renderer/rescan-button.js`: tracks in-flight rescans per collection id in a renderer `Set`, disables the button while the selected collection has one running, and ignores a result for a collection no longer selected.
- `src/renderer/tree-view.js` and `src/shared/tree-model.js`: nodes are identified by `<rootFolderId>:<relativePath>`; selection (`selectedId`) is a node id; `show` clears the selection, `update` keeps it only if the node id still exists. `buildTree` builds one root per folder record and does not de-duplicate: two roots that overlap show the same file under both, with different node ids. The file-detail module (`src/renderer/file-detail.js`) shows the path of the selected file and a Reveal button.
- Tests: `tests/support/background-main.js` runs the app hidden (accessory activation policy, `show: false` windows) and replaces `shell.showItemInFolder` with a recording stub; `tests/support/e2e-app.js` has `launchApp`, `selectOnlyCollection`, `stubFolderPicker` and `gateChannel`; `tests/support/ipc-wrap.js` wraps a recorded `ipcMain.handle` handler; `tests/support/fixture-tree.js` builds a fixture tree with a manifest; `tools/readonly-check` (`snapshot`, `compare`, `assert`) compares contents, timestamps and extended attributes, and `tests/e2e/reveal-readonly.spec.js` runs it around a flow with the app closed for the snapshots. Unit tests run under Vitest in `tests/unit/`, e2e under Playwright in `tests/e2e/`.
- Not measured: how large a user's real store is, and what a version-1 store with real data looks like beyond the record shapes above.

## Goals
- A user can rename a collection, delete a collection, add a folder to an existing collection, and remove a folder from a collection, and the result is still there after a restart.
- A user can switch the active collection, and every view then shows only that collection's files.
- The same folder can be a member of more than one collection, and deleting a collection or removing a folder never removes index data another collection still uses.
- Adding a folder that is inside a folder already in the collection is refused with a message naming the covering folder. Adding a folder that contains folders already in the collection asks for confirmation naming them and replaces them; cancelling changes nothing. Creating a collection from nested picks keeps only the outermost picks and tells the user what was dropped.
- A file reachable through more than one folder in the same collection appears once (also for older stored collections that still hold nested folders), and no action in this feature changes anything inside a collection's folders.

## Non-goals
- Flat views by media type (Feature 4); this feature only fixes the rule that a file appears once, so those views can rely on it.
- Scan progress and browsing while a scan runs (Feature 5), and any change to what a rescan scans.
- Moving or copying files between folders, or anything that creates, moves, renames or deletes a file on disk (product FR-17).
- Reordering collections, merging collections, duplicating a collection, and exporting or importing collections.
- Tags, favorites and ratings (v1), and encryption of app storage.

## User stories
- US-1: As a creative professional, I want to group folders from different drives into named collections, rename or delete them, and add or remove folders so that each project or archive has its own workspace. (Product US-1.)
- US-2: As a creative professional, I want to switch between collections so that I only see the media relevant to the current job. (Product US-2.)
- US-3: As a creative professional, I want to be sure the app never changes my files so that I can point it at irreplaceable archives. (Product US-3.)
- US-4: As a hobbyist, I want to see each file once in my lists even when my folders overlap so that the folder structure doesn't get in the way. (Product US-5, cited by product FR-6.)

## Functional requirements
1. FR-1: Users MUST be able to rename a collection. The new name MUST be shown in the collection list immediately and MUST be present after the app is quit and relaunched. The rules are the same as at creation: leading and trailing whitespace is trimmed; an empty or whitespace-only name is rejected with an error and the name is left unchanged; duplicate names are allowed; there is no maximum length. Renaming MUST NOT change the collection's folders or index. [US-1] (Product FR-2.)
2. FR-2: Users MUST be able to delete a collection. The app MUST always ask for confirmation first, and the confirmation MUST state that no files on disk are touched; cancelling changes nothing. After a confirmed delete the collection MUST disappear from the list and MUST NOT return after a relaunch. When the deleted collection is the active one, no collection is active afterwards and the tree and the file selection are cleared. Deleting a collection MUST NOT delete any file or folder on disk. [US-1] [US-3] (Product FR-2.)
3. FR-3: Users MUST be able to remove a folder from a collection. After removal the folder MUST NOT appear in that collection's tree, and the change MUST persist across a relaunch. When the folder belongs to the active collection, the tree MUST be refreshed in place and the file selection kept only if its node id still exists (the existing `TreeView.update` rule). Removing a folder MUST NOT delete anything on disk. Removing the last folder of a collection MUST be refused, with a message suggesting that the user delete the collection instead; the collection is left unchanged. [US-1] [US-3] (Product FR-2.)
4. FR-4: Deleting a collection or removing a folder MUST delete that collection's own records only: the collection (for delete), the folder records and their index and access data. It MUST NOT touch any record belonging to another collection. Because the same folder path in two collections is two separate `FolderRecord`s (FR-6), each with its own index, "entries no other collection still uses" holds by construction. `removeFolder` and `removeCollection` MUST keep `CollectionRecord.folderIds` consistent: removing a folder removes its id from the owning collection's `folderIds`, and adding a folder appends it (neither is done by the shipped code). A folder, collection or other collection's tree that was not named by the action MUST be unchanged. Constraint for Feature 6, not built here: any cache shared across collections MUST be keyed by path, and an entry MUST be deleted only after checking the index records of all collections for a remaining use. [US-1] (Product FR-2, FR-4; Feature 3 notes.)
5. FR-5: Users MUST be able to switch the active collection by choosing it in the collection list. After a switch, every view MUST show only files from that collection's folders and no file of the previously active collection. A switch MUST NOT trigger a scan, and a selection from the previous collection MUST NOT remain selected. At launch no collection is active (as today). The active collection is not persisted; remembering the last-used collection is deferred. [US-2] (Product FR-3.)
6. FR-6: The same folder (the same absolute path) MUST be allowed in more than one collection, whether chosen at collection creation or added later. Each membership is its own `FolderRecord` (different id, its own `collectionId`) with its own index. The version-1 store format is kept: there is no format bump and no migration, and an existing version-1 store MUST open unchanged. Adding a folder to one collection MUST NOT change any other collection's folders, index or tree. Known cost, stated as a fact: a folder shared by several collections is scanned and stored once per collection, and the copies can differ until each collection is rescanned. [US-1] (Product FR-4.)
7. FR-7: Users MUST be able to add a folder to an existing collection using the same directories-only folder picker and the same readability rejection as collection creation (Feature 1 FR-1, OQ-10 there): a folder that cannot be opened for listing MUST be rejected with an error naming the folder, and the collection MUST be left unchanged. The added folder MUST be scanned and indexed (only the new folder is scanned, not the collection's other folders), and MUST be present after a relaunch. [US-1] (Product FR-27.)
8. FR-8: Before a folder is added, its path MUST be compared with the collection's existing folders. Paths are normalised with `path.resolve`, symlinks are resolved with `realpath` for folders that exist, and the comparison is case-insensitive and by whole path segments (`/a/b` is not inside `/a/bc`; a trailing slash does not matter). A false overlap on a case-sensitive volume only produces a refusal or a replace prompt that the user can avoid. Revised 2026-10-21 (product FR-5): a collection MUST NOT hold a folder that is inside another of its folders. The rules are as follows. (1) Inside: when the folder being added sits inside a folder already in the collection, `addFolder` MUST refuse. The error names the folder that covers it and says the folder is already covered. Nothing is written and no scan runs. There is no confirmation dialog. (2) Identical: an identical path (the same folder again after normalisation) MUST be refused the same way, with a message saying the folder is already in the collection. (3) Contains: when the folder being added contains one or more folders already in the collection, the app MUST show a confirmation that names the contained folder(s) and says they will be replaced. On confirm, one storage transaction MUST add the new folder (and append its id to `folderIds`) and remove the contained folder records from this collection (each with its index and access data, and its id from `folderIds`), using the same cleanup rule as FR-3 and FR-4, so records of other collections for the same paths are untouched. The new outer folder is then scanned and its index stored; if that scan fails the folder is stored with `unavailable: true` and an empty index, as for any add (FR-7). On cancel, the collection MUST be unchanged: no folder record, no index entry, no scan. The replace MAY remove every existing folder; the last-folder refusal of FR-3 does not apply, because the new folder is added in the same transaction. A selection in a replaced folder is cleared by the existing `TreeView.update` rule, because its files now have new node ids under the new outer root. (4) At creation: when the picked folders nest, every picked folder that is inside another picked folder MUST be dropped. The collection is created with only the outermost picks, with no confirmation dialog. The result MUST tell the user which folders were dropped and which picked folder covers each, and the renderer MUST show that notice. Identical picks already collapse (existing behaviour) and are not reported as nesting. The two `describeOverlap` wordings of the shipped code ("already covered", "the collection already contains a folder inside the one being added") are replaced by the refusal, replace and notice texts above. [US-1] (Product FR-5, FR-27.)
9. FR-9: A file reachable through more than one folder of the same collection MUST appear once in that collection's views. When two roots overlap, the outer (containing) root owns the file and the inner root drops it. For identical-path roots in one collection the folder earliest in `CollectionRecord.folderIds` (the earliest added) owns the file and the others drop it. This is computed when the tree is built, not in storage, so it holds after adding a folder, after a rescan and after a relaunch. Since 2026-10-21, FR-8 prevents new nested or identical roots, so this rule is a safety net for legacy data only: collections stored before the revision (store version 1, written by Feature 1 or by the earlier confirm-and-keep-both behaviour) can still hold nested or identical roots. They MUST keep showing each file once. No migration rewrites them and the store format is unchanged. For such data roots are always shown, so an inner root stays visible, possibly empty. Removing the outer root makes the files appear under the inner root without any stored change; a selected node whose id disappears is cleared by the existing update rule. Selection of a file (Feature 2 FR-1, keyed by node id `<rootFolderId>:<relativePath>`) MUST still identify exactly one row. [US-4] (Product FR-6.)
10. FR-10: Every action in this feature (rename, delete, add folder, remove folder, switch, a refused add and a cancelled add) MUST NOT create, modify, move, rename or delete any file, folder or extended attribute inside a collection's folders. Tests MUST run the Feature 1 read-only check (`tools/readonly-check`) around each of these flows on a fixture tree and the check MUST report no differences. [US-3] (Product FR-17.)
11. FR-11: A failed, refused or cancelled action MUST leave the persisted store unchanged. Each action that changes stored data (rename, delete, add folder, remove folder) MUST be applied in one storage transaction so a failure part-way leaves no partial state; the `folderIds` update of FR-4 is part of that transaction, and so is the removal of replaced folders in FR-8. [US-1] (Supports product FR-2, FR-27.)
12. FR-12: While a collection's rescan or add-folder scan is running, add-folder, remove-folder, rename and delete for that collection MUST be refused with a clear error, and the renderer MUST disable those controls. The existing main-process in-flight guard (per collection id, `RESCAN_IN_PROGRESS`) MUST be extended so a rescan and an add-folder scan of the same collection exclude each other; a second rescan of the same collection is still rejected. Other collections are unaffected. [US-1] (Supports product FR-26 behaviour of Feature 1.)
13. FR-13: Unit tests MUST cover: the storage operations for rename, delete, add folder and remove folder, including that another collection's records for the same path are untouched and that `folderIds` stays consistent (FR-4); the overlap detection in both directions (inside and contains) and the non-overlap case, with these path cases: inside, contains, unrelated, `/a/b` vs `/a/bc`, trailing slash, case difference, symlink; refuse-inside and refuse-identical (error text, nothing written, no scan, no confirmation asked); replace-on-contains (one transaction, the contained folder records, their index and access data and `folderIds` entries removed, the new folder stored and scanned, cancel leaves the store unchanged, replacing every existing folder is allowed, and another collection's records for the same path are untouched); the creation drop-nested notice (outermost picks kept, dropped folders and their covering folder reported, no confirmation); the one-appearance rule of FR-9 including the identical-path tie-break, kept as the safety net for legacy nested data; the last-folder refusal; and the in-flight refusals of FR-12. End-to-end tests MUST cover each flow through the UI, including refuse-inside, refuse-identical, replace-on-contains with confirm and with cancel, the creation drop-nested notice, and the one-appearance rule on a store seeded with nested roots, MUST run through `tests/support/background-main.js` so no window is brought to the front, MUST stub the folder picker (`stubFolderPicker`), and MUST include a quit-and-relaunch check of each persisted change. [US-1] [US-2] [US-4] (Product FR-2 to FR-6, FR-27; repository e2e convention.)

## Open questions
- OQ-1 [Resolved 2026-10-20]: Data model for a folder shared by several collections (FR-6). Does the change need a new store format version, and what happens to an existing version-1 store? — Impact: FR-4, FR-6, FR-11, and the storage module and `startStorage` messages. Owner: product owner (user), with the implementer for the migration mechanics.
  Answer: Option a. Keep the version-1 store format. No format bump and no migration; an existing v1 store opens unchanged. The same folder path in two collections is two separate `FolderRecord`s (different ids, each with its own `collectionId`). SQLite or a later format remains the recorded future option (FR-6).
- OQ-2 [Resolved 2026-10-20]: Is a folder shared by two collections indexed once or once per collection, and what does "delete entries no other collection still uses" mean? — Impact: FR-4, FR-6, FR-12, and the cache of Features 6 to 8. Owner: product owner (user), with the implementer.
  Answer: Option a. Indexed once per collection, with separate indexes. Deleting a collection or removing a folder touches only that collection's records, so "entries no other collection still uses" holds by construction. Known cost, a fact: a shared folder is scanned and stored once per collection and the copies can differ until each is rescanned. Feature 6 must key any shared cache by path and check all collections' index records before deleting an entry (constraint noted in FR-4, not built here). `removeFolder` and `removeCollection` must keep `CollectionRecord.folderIds` consistent (FR-4).
- OQ-3 [Resolved 2026-10-20]: De-duplication rule (FR-9): which root owns a file reachable through two roots of the same collection? — Impact: FR-9, and Feature 2 selection; Feature 4 flat views. Owner: product owner (user).
  Answer: Option a. The outer (containing) root owns the file and the inner root drops it, computed when the tree is built, not in storage. Roots are always shown, so the inner root stays visible, possibly empty. Removing the outer root makes the files appear under the inner root with no stored change; a selected node whose id disappears is cleared by the existing update rule. Identical-path roots follow the same rule with a deterministic tie-break: the earliest added (first in `folderIds`) owns the file (FR-9).
  Revised 2026-10-21: the rule stays, but only as a safety net for collections stored before the revision. New nested or identical roots can no longer be created (FR-8), so an inner root that shows empty can only occur in legacy data. No migration rewrites such data (FR-9).
- OQ-4 [Resolved 2026-10-20]: Overlap detection (FR-8): path comparison rules, dialog content, and whether the check applies at creation. — Impact: FR-6, FR-8, FR-13. Owner: product owner (user), with the implementer for path normalisation.
  Answer: Option a. Dialog content is fixed by product FR-5: inside an existing folder gives "already covered"; containing an existing folder gives "the collection already contains a folder inside the one being added"; confirm keeps both; cancel writes nothing. Paths are compared after `path.resolve`, with `realpath` for roots that exist, case-insensitively and by whole path segments (`/a/b` is not inside `/a/bc`). The dialog names the overlapping folder. The same confirmation applies at collection creation when the picked folders overlap each other. An identical path counts as "already covered". Unit tests cover inside, contains, unrelated, `/a/b` vs `/a/bc`, trailing slash, case difference and symlink (FR-8, FR-13).
  Revised 2026-10-21, after the hands-on check (the user confirmed adding a folder inside an existing one; both roots stayed and the inner root showed nothing when expanded, which read as a bug). The path comparison above is unchanged. The dialog content is replaced: inside, and identical, are refused with a message naming the covering folder (identical: already in the collection), with no dialog, no write and no scan; containing asks for confirmation naming the contained folders and saying they will be replaced, and on confirm one transaction adds the new folder and removes the contained ones, then scans the new folder; cancel writes nothing; at creation, nested picks are dropped without a dialog and the user is told what was dropped and what covers it (FR-8). The confirmation wording "confirm keeps both" no longer applies.
- OQ-5 [Resolved 2026-10-20]: Delete-collection confirmation and what is shown after deleting or removing (FR-2, FR-3, FR-5). — Impact: FR-2, FR-3, FR-5. Owner: product owner (user).
  Answer: Option a. Always confirm before deleting a collection, stating that no files on disk are touched. After deleting the active collection none is active and the tree and selection are cleared. Removing a folder of the active collection refreshes the tree in place, keeping the selection only if its node id still exists (FR-2, FR-3).
- OQ-6 [Resolved 2026-10-20]: Rename rules (FR-1). — Impact: FR-1. Owner: product owner (user).
  Answer: Same as creation, from `src/main/collections/service.js:115,131`: trim leading and trailing whitespace; reject empty or whitespace-only; duplicate names allowed; no maximum length (FR-1).
- OQ-7 [Resolved 2026-10-20]: Which collection is active at launch, and does the active collection persist? — Impact: FR-5, and the stored data shape. Owner: product owner (user).
  Answer: Option a. At launch none is active (as today). The active collection is not persisted. Remembering the last-used collection is deferred (FR-5).
- OQ-8 [Resolved 2026-10-20]: Removing the last folder from a collection (FR-3). — Impact: FR-3, FR-2. Owner: product owner (user).
  Answer: Option a. Refused, with a message suggesting deleting the collection instead (FR-3).
- OQ-9 [Resolved 2026-10-20]: Rescan and add-folder interactions (FR-12). — Impact: FR-7, FR-12, FR-3, FR-2. Owner: implementer, with the product owner (user).
  Answer: Option a. While a collection's rescan or add-folder scan runs, add-folder, remove-folder, rename and delete for that collection are refused with a clear error; the existing main-process in-flight guard is extended so rescan and add-folder scans exclude each other, and the renderer disables those controls. An add-folder scans only the new folder (FR-7, FR-12).

## Out of scope (deferred)
- Flat views by media type (Feature 4); they rely on the one-appearance rule of FR-9.
- Scan progress, incremental publishing and browsing during a scan (Feature 5).
- Preview, playback and the capped cache (Features 6 to 8); FR-4 names cache entries so those features inherit the rule.
- Numeric performance targets (product FR-20, after the measurement task).
- Reordering, merging, duplicating, exporting or importing collections.
- Live index updates, hidden-file options and files on disconnected drives being hidden (v1).
