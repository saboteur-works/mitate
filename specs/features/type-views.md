# Feature Spec: Browse by media type

**Source:** Feature 4 in `specs/product/media-organizer-mvp.features.md`
**Product spec:** `specs/product/media-organizer-mvp.md` (product FR-11; FR-6 and FR-17 apply; FR-20 is blocked on measurement and is not promised here; product US-5; Constraints: read-only, macOS first)
**Branch:** `feat/type-views`
**Depends on:** Feature 1 (`specs/features/collection-index-tree.md`, shipped), Feature 2 (`specs/features/location-reveal.md`, shipped) and Feature 3 (`specs/features/collection-management.md`, shipped; its one-appearance rule is relied on here). IDs below are local to this document. Each requirement names the product requirement it implements.
**Length note:** This spec is longer than the 500-word guideline. It covers one product requirement but must also record the shipped seams (tree, selection, detail area, view IPC, registry) it reuses, and eight open questions, all resolved 2026-10-21.

## Overview
A user who wants to see "all my photos" or "all my audio" in a collection, without walking the folder tree, can open four flat lists, Images, Audio, Video and Documents. Each list spans every folder of the active collection and shows each file once. Selecting a file in a list behaves as it does in the tree: its path is shown and Reveal in Finder works on it. Today the only view is the folder tree, and a user who wants every image has to expand folders one by one. Lists over hundreds of thousands of files are the normal case for the primary audience, so a list must not render or lay out one element per file. Nothing in this feature changes anything on disk.

## State of the shipped code (measured by reading the code, 2026-10-21)
- Supported-type registry, `src/main/registry/types.js` (FR-8): `KINDS` is `['image', 'audio', 'video', 'document']`. A table maps lowercase extension to kind, with subtype `RAW` for twelve RAW extensions (kind `image`). Documents are `pdf`, `txt`, `epub`, `cbz`. `lookupFileName` is case-insensitive on the extension. `listByKind(kind)` throws on an unknown kind. The registry is a CommonJS module in the main process only; the renderer has no copy of it.
- Every `FileRecord` carries `kind` (copied from the registry at scan time). The scanner stores supported files only, so no stored record has an unknown kind (`src/shared/tree-model.js` header). Hidden files, package bundles and symlinks are skipped by the scan (product FR-9).
- `src/main/collections/service.js` `collectionView(storage, collectionId)` returns `{ collection, folders, files }`: `folders` are ordered, with `resolvedPath`; `files` are all file records of all folders of the collection, each of an unavailable folder carrying `unavailable: true`. IPC `collections:getView` returns it as `{ ok, view }`. There is no query by kind, no count, and no paging: the whole index of the collection crosses IPC on every view load. `collections:rescan` and `collections:addFolders` also return a `view`.
- `src/shared/tree-model.js`: `buildTree(folderRecords, fileRecords)` builds one root per folder record and de-duplicates (FR-9 of Feature 3): a root drops a file when an owner root (a root that strictly contains it, or an identical-path root earlier in `folderIds`) has a record for the same absolute path; keys are case-sensitive over `resolvedPath || path`. Since 2026-10-21 new nested or identical roots cannot be created, so this is a safety net for stored legacy data. A file node id is `<rootFolderId>:<relativePath>`. Nothing outside the tree consumes the de-duplication; a flat list built straight from `files` would show a file twice for legacy nested roots.
- `src/renderer/tree-view.js`: a virtualized view. Only rows in the viewport plus 5 rows of buffer are in the DOM, a spacer of `rows * 24px` gives the scroll range, and rows are absolutely positioned. Selection is one node id (`selectedId`); clicking a file row or pressing Enter or Space on a focused file selects it and dispatches `file-selected` on `document` with `detail.file` (`nodeId`, `path`, `name`, `folderId`, `relativePath`, `kind`, `unavailable`) or `null`. Focus is a node id; the container is the single Tab stop (`role="tree"`, `tabindex` 0) and `aria-activedescendant` points at the focused row, which stays rendered outside the window. ArrowUp and ArrowDown move without wrapping. `show(folders, files)` clears the selection; `update(folders, files)` keeps it only if the node id still exists. Both dispatch `tree-updated`. `flattenVisible` builds the full visible row array, so the tree is virtualized in the DOM but holds a row object per visible node.
- `src/renderer/file-detail.js` and `src/shared/file-detail.js`: the detail area listens for `file-selected`, shows the selected file's full path, and enables a Reveal in Finder button that calls `window.mediaOrganizer.revealFile(path)`. It clears its error on selection change and on `tree-updated`. It reads nothing from the tree except the event, so any view that dispatches `file-selected` drives it.
- `src/renderer/create-collection.js` and `collection-manage.js`: choosing a collection in the list calls `collections:getView`, a token drops a stale slower response, `TreeView.show` is called, and `collection-selected` is dispatched on `document` with `detail.collectionId`. A rescan, add-folder or remove-folder on the active collection calls `TreeView.update`. At launch no collection is active. `index.html` has one "Tree" section (rescan button, status, `tree-view` container) and one "File location" section. There is no tab, toggle or other control to switch views.
- README: lists the virtualized tree, selection and Reveal; it does not mention type views.
- Tests: `tests/support/background-main.js` runs the app hidden (`show: false`, accessory activation policy) and stubs `shell.showItemInFolder`; `tests/support/e2e-app.js`, `fixture-tree.js` and `tools/readonly-check` exist as in Feature 3. Unit tests run under Vitest, e2e under Playwright.
- Not measured: the time to filter, de-duplicate and sort a list of hundreds of thousands of records in the main process or the renderer; the memory of holding one row object per file; how many files a real collection has per kind. `docs/measurements/json-store-scale.md` measures the JSON store at 50,000, 200,000 and 500,000 records, not view building. Product FR-20 gives no numeric target, so none is promised here.

## Goals
- A user with an active collection can open an Images, an Audio, a Video and a Documents list, each showing every file of that kind from every folder of the collection.
- A file appears once in these lists, including in collections stored with nested or identical folders.
- A list over hundreds of thousands of files scrolls through the whole list without one DOM element per file.
- A user can select a file in a list by click or keyboard, and the detail area and Reveal in Finder apply to it as they do for a tree selection.
- Switching between views and viewing a list change nothing inside a collection's folders.

## Non-goals
- Search, filtering by name, extension, size or date, grouping, and user-chosen sort. Sorting beyond the one fixed order of FR-4 is not part of this feature.
- Thumbnails, preview and playback (Features 6 to 8); rows show text only.
- Updating the lists while a scan runs (Feature 5); see the forward constraint under FR-9.
- Multi-select, and any action on a file other than select and Reveal.
- Changing what the scan indexes, the registry's extension-to-kind map (OQ-7), or the tree view's behaviour.
- Numeric performance targets (product FR-20), and any change to files on disk (product FR-17).

## User stories
- US-1: As a hobbyist, I want to see all my images, audio, video and documents as flat lists by type so that the folder structure doesn't get in the way. (Product US-5.)
- US-2: As a hobbyist, I want to see a file that sits under overlapping folders only once in each list so that I do not see duplicates. (Product US-5, through product FR-6.)
- US-3: As a creative professional, I want to see where a file in a list lives and reveal it in Finder so that I can work with it in other apps. (Product US-6, reusing Feature 2.)
- US-4: As a creative professional, I want to know that browsing by type never changes my files so that I can point the app at irreplaceable archives. (Product US-3, through product FR-17.)

## Functional requirements
1. FR-1: For the active collection the app MUST offer four views, Images, Audio, Video and Documents, in addition to the existing tree view. Each view MUST list every file of that kind (`image`, `audio`, `video`, `document` as stored on the file record) from every folder of the collection, at any depth, and no file of another kind or of another collection. The user switches views with a row of tabs (Tree, Images, Audio, Video, Documents) with `role="tablist"` over one shared view area; each tab has `role="tab"` and `aria-selected`, and the view area has `role="tabpanel"`. The tabs MUST be keyboard operable per the WAI-ARIA tabs pattern (one Tab stop on the tab row, ArrowLeft and ArrowRight move between tabs, Home and End go to the first and last tab). The Rescan button and its status sit above the view area and apply to the collection in every view, and the section heading "Tree" is renamed to suit a section that holds several views (OQ-1, OQ-8). [US-1] (Product FR-11.)
2. FR-2: Each file MUST appear once in a list. The files of a list MUST be those the tree would show for the same collection: the owner rule of Feature 3 FR-9 (the outer root owns a file; for identical roots the earliest in `folderIds` owns it; case-sensitive comparison of the native-realpath-resolved paths) applies to the lists. A file reachable through two folders of one collection MUST NOT appear twice in one list, and MUST NOT be missing from every list. The rule MUST be implemented once and used by both the tree and the lists, not copied. [US-2] (Product FR-6; Feature 3 FR-9.)
3. FR-3: Each list MUST be virtualized. The number of file elements in the DOM MUST depend on the viewport height and a fixed buffer, not on the number of files. The list MUST give the scrollbar the range of the whole list, so the user can reach the last file by scrolling or by keyboard, and the view MUST be usable with a list of 500,000 files (the largest size the store has been measured at). This requirement states a structure, not a speed: no time or memory target is promised (product FR-20 is blocked on measurement). [US-1] (Product FR-11, FR-20; feature list note on scale.)
4. FR-4: Each list MUST have one fixed, deterministic order, and ties MUST be broken deterministically so the same data gives the same order on every load. A row MUST be one line per file showing the name, with the folder as a dimmed second part of the same row: the folder's path relative to the collection root, or the root folder's name for a top-level file. The order is by name using the tree's `compareNames` (natural numeric, case-insensitive), with ties broken by absolute path (OQ-2). Two files with the same name from different folders MUST both be shown and are distinguishable by the folder part of the row. [US-1] (Product FR-11.)
5. FR-5: A file row MUST be selectable by click, and by Enter or Space when focused. At most one file is selected at a time, and the selection MUST be held as the file's node id (`<rootFolderId>:<relativePath>`, the same id the tree uses), not as a row index, so it survives scrolling and re-rendering. Selecting MUST dispatch `file-selected` on `document` with the same `detail.file` shape the tree dispatches, so the detail area and Reveal in Finder show and act on the selected file with no change to their contract (Feature 2 FR-1 to FR-5). Clearing the selection MUST dispatch `file-selected` with `detail.file` null. [US-3] (Product FR-15, FR-16.)
6. FR-6: A list MUST be keyboard operable on the model of the tree: one Tab stop, an `aria-activedescendant` that points at the focused row, ArrowUp and ArrowDown moving the focus without wrapping and scrolling it into view, and the focused row always rendered even when scrolled outside the virtual window. The container and rows MUST carry roles that a screen reader announces as a list or listbox with selectable items (the exact roles are an implementation choice), and `aria-selected` MUST reflect the selection. Home and End jumping to the first and last row MUST work, because a 500,000-row list is not reachable by arrow keys in practice. [US-1] (Product FR-11; Feature 1 keyboard decisions.)
7. FR-7: Switching view MUST clear the selection and dispatch `file-selected` with `detail.file` null (OQ-3); no selection carries from one view to another. The selection MUST also be cleared, with `file-selected` null, when the active collection changes, and MUST never refer to a file that is not in the displayed collection. When a view is rebuilt for the same collection (after a rescan, add-folder or remove-folder), the selection MUST be kept only if its node id is still among the files of the displayed view, as `TreeView.update` does. [US-3] (Product FR-15; Feature 3 FR-5.)
8. FR-8: A file of an unavailable folder MUST be listed, flagged with the same visible "unavailable" label the tree uses, and not hidden. A list with no files MUST say so in text (not leave an empty area), and the text MUST be "No <kind> files in this collection", with the kind in plain words (image, audio, video, document) (OQ-5). Hiding the files of unavailable folders is ruled out by Feature 1 FR-4. Files of unknown kind are not indexed and appear in no view; no skipped-file count is shown (OQ-4; a count, if ever wanted, is a later feature). [US-1] (Product FR-11; Feature 1 FR-4.)
9. FR-9: The views MUST be refreshed from the same data as the tree after a rescan, an add-folder, a remove-folder or a replace, so a list never shows a file the tree does not (and the reverse) for the same collection and the same load. Forward constraint for Feature 5, not built here: the views will have to stay correct while a scan runs (results arriving incrementally, counts changing under the user), so the list and its selection MUST NOT assume the file set is fixed for the lifetime of the view; they MUST take their data through one update path that Feature 5 can feed. [US-1] (Product FR-11, FR-18.)
10. FR-10: The lists MUST be built in the renderer from the `view.files` the window already receives (OQ-6), using the one-appearance rule of FR-2 extracted from `buildTree` into a shared function used by both. Each kind's sorted list MUST be computed lazily on the first open of that tab and cached per collection load; the cache MUST be invalidated when the view is rebuilt (rescan, add-folder, remove-folder, replace, collection change). No new IPC channel is added and the per-load payload is unchanged by this feature; reducing that payload belongs with FR-20 and Feature 5. The first open of a kind MAY show a loading state while the list is sorted, and the window MUST NOT otherwise be blocked without the user seeing that state (see the measurements under OQ-6). A slower response for a previous collection or a previous view MUST be discarded (the token rule of `selectCollection`). [US-1] (Product FR-11, FR-20.)
11. FR-11: Switching view MUST NOT trigger a scan, a rescan, or any write of the store, and MUST NOT disturb the other views' expansion state (the tree's expanded folders and scroll position MUST be the same on return to the tree within one session; the selection is cleared on a switch, FR-7). At launch no collection is active and no list is shown, as today. The last-used view is not persisted. [US-1] (Product FR-11; Feature 3 FR-5.)
12. FR-12: Browsing by type MUST NOT create, modify, move, rename or delete any file, folder or extended attribute inside a collection's folders. Opening each of the four views, scrolling, selecting and revealing in them MUST be covered by the existing read-only check (`tools/readonly-check`), run around a flow on a fixture tree with the app closed for the snapshots, and it MUST report no differences. [US-4] (Product FR-17.)
13. FR-13: Unit tests MUST cover: the selection of files by kind for each of the four kinds, including RAW files (kind `image`) and an uppercase extension; that a list holds no file of another kind; the one-appearance rule through the shared rule of FR-2 for nested roots, identical-path roots and a case-differing pair (kept distinct), with the same files as the tree for the same input; the order and tie-break of FR-4 including equal names from different folders and natural numeric order; the windowing arithmetic of FR-3 (rows in the DOM for 0, 1, a viewport's worth and 500,000 rows); node-id selection surviving re-render; selection cleared on collection change and kept on rebuild only when the id exists (FR-7); the unavailable flag; the empty state. End-to-end tests MUST open each view through the UI, select a file by click and by keyboard and check the detail area and a recorded Reveal call, check a list over a generated fixture of at least 10,000 files for a bounded number of row elements in the DOM and for reaching the last row with End, check a legacy store seeded with nested roots (each file once), run through `tests/support/background-main.js` so no window is brought to the front, and include the read-only check of FR-12. [US-1] [US-2] [US-3] [US-4] (Product FR-11, FR-17; repository e2e convention.)

## Open questions
- OQ-1 [Resolved 2026-10-21]: How does the user switch between the tree and the four views? — Impact: FR-1, FR-11, FR-13, `index.html`, and Feature 5's progress placement. Owner: product owner (user).
  Answer: Option a. A tab row (Tree, Images, Audio, Video, Documents) with `role="tablist"` over one shared view area. Tabs are keyboard operable per the WAI-ARIA tabs pattern (FR-1).
- OQ-2 [Resolved 2026-10-21]: What is the sort order of a list and which columns does a row show? — Impact: FR-4, FR-3 (row height), FR-13. Owner: product owner (user).
  Answer: Option a. One row per file showing the name, with the folder (path relative to the collection root, or the root folder's name for top-level files) as a dimmed second part of the same row. Order is name by the tree's `compareNames` (natural numeric, case-insensitive), ties broken by absolute path (FR-4).
- OQ-3 [Resolved 2026-10-21]: Does the selection carry across views? — Impact: FR-5, FR-7, FR-11, FR-13. Owner: product owner (user).
  Answer: Option c. Switching view clears the selection (`file-selected` null). The tree's expansion state and scroll position are still kept within a session (FR-7, FR-11).
- OQ-4 [Resolved 2026-10-21]: Do files of unknown kind (extension not in the registry) appear anywhere? — Impact: FR-1, FR-8, FR-13. Owner: product owner (user).
  Answer: Option a. Unsupported files are not indexed and appear nowhere. A skipped-file count, if ever wanted, is a later feature (FR-8).
- OQ-5 [Resolved 2026-10-21]: What do the empty and unavailable-folder states say? — Impact: FR-8, FR-13. Owner: product owner (user).
  Answer: Option a. An empty list shows "No <kind> files in this collection" (kind in plain words: image, audio, video, document). Files of unavailable folders are listed with the tree's "unavailable" label; hiding them is ruled out by Feature 1 FR-4 (FR-8).
- OQ-6 [Resolved 2026-10-21]: Where are the views computed, in the main process or in the renderer? — Impact: FR-2, FR-3, FR-9, FR-10, FR-13, the IPC surface. Owner: implementer, with the product owner (user).
  Answer: Option a. Lists are built in the renderer from the `view.files` the window already receives, using the shared one-appearance rule extracted from `buildTree`. Each kind's sorted list is computed lazily on first open of that tab and cached per collection load; the cache is invalidated when the view is rebuilt (rescan, add, remove, collection change). FR-10 allows the first open of a kind to show a loading state while sorting. Reducing the per-load payload belongs with FR-20 and Feature 5 (FR-2, FR-10).
  Measurement (fact; the data is synthetic and real collections may differ). Setup: measured 2026-10-21 on this Mac, Node 24.15 (the same V8 as Electron 44), synthetic records under one root, real `compareNames` and `buildTree`. Filtering one kind: 3-5 ms at 500k files. Sorting 250k files of one kind by `compareNames` plus a path tie-break: 678-743 ms. `buildTree` over 500k files: 998 ms. `JSON.stringify` of 500k file records: 86 MB, which is the existing per-load IPC payload. At 100k files: sort 106-125 ms, `buildTree` 162 ms, 17 MB.
- OQ-7 [Resolved 2026-10-21]: Does the Documents kind include text files? — Impact: FR-1, FR-13, the registry. Owner: product owner (user).
  Answer: Option a. Keep the registry. Documents are pdf, txt, epub and cbz, so `.txt` files are listed under Documents (FR-1).
- OQ-8 [Resolved 2026-10-21]: Where do the Rescan button and its status live once there are several views? — Impact: FR-1, FR-11, `index.html`. Owner: implementer.
  Answer: Option a. The Rescan button and status sit above the view area and apply in every view. The "Tree" heading is renamed to suit (FR-1).

## Out of scope (deferred)
- Views that update while a scan runs and the progress indicator (Feature 5); FR-9 states the constraint they must meet.
- Thumbnails, preview and playback (Features 6 to 8).
- Search, filter, grouping and user-chosen sort order.
- Showing file size or modified date (not stored today).
- Remembering the last-used view or collection across launches.
- Numeric performance targets (product FR-20, after the measurement task).
